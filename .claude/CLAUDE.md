# 実行環境

この `~/.claude/CLAUDE.md` は dotfiles 経由で **全マシン共通**に配布される。Claude Code は下記3台のいずれでも動くため、**今どのマシンで動いているかを必ず `hostname` で判定する**こと。取り違えないこと。

## 全体構成

```
[Windows]  →  [WSL2 (Ubuntu)]  →  [Nucbox (Ubuntu, mini PC)]
 WezTerm GUI     mosh/ssh で接続       mosh/ssh で接続
```

`hostname` による判定：

- `tomoki-NucBox-G10` → Nucbox（mini PC）
- それ以外 → WSL2 か Windows ネイティブ

3 台すべてで dotfiles と Claude Code が動く。

## 含意（取り違えやすいポイント）

- 実行するシェルコマンドは**今いるマシンのローカル**で走る。Nucbox には `/mnt/c/...` のような Windows パスは無い（WSL2 には存在する）。
- WezTerm GUI 本体は Windows 上で動いている。Nucbox / WSL2 側で `~/dotfiles/.config/wezterm/` を編集しても**手元の表示には即反映されない**（dotfiles を Windows 側にデプロイして初めて効く）。
- IME（Windows IME / Mozc）も Windows 側にある。Nucbox など遠隔の Linux マシンから IME を制御したい場合は OSC エスケープシーケンス経由でローカル WezTerm に通知する構成になる（`im-select.exe` 等は Linux マシンには無い）。

# grep 禁止（ripgrep / ag を使う）

シェルから `grep` / `egrep` / `fgrep` / `zgrep` 系を **実行してはいけない**。
`PreToolUse` hook（`.claude/hooks/deny-grep.py`）と `permissions.deny` の両方でブロックされる。
巨大ファイルでの OOM と、Node プロセスの多重起動によるメモリ枯渇を防ぐため。

<!--
理由の詳細（人向けのメモ。HTML コメントは Claude のコンテキストに載る前に取り除かれる）

- GNU grep は改行の無い巨大ファイル（minified JS・ログ・バイナリ）に当たると 1 行をまるごとメモリに載せ、数 GB を確保して OOM を起こす。
- さらに Claude Code はシェルスナップショットで `grep` を関数として乗っ取り `claude -G`（Node 製 ugrep）へ転送するため、grep 1 回ごとに Node プロセスが立ち上がる。パイプやループで多重起動するとメモリ上限のあるマシン（NucBox の `user-1000.slice` は 10G 上限）を簡単に食い潰す。
-->

## 代替

| やりたいこと | 使うもの |
| --- | --- |
| ファイル内容の検索 | Grep ツール（内蔵 ripgrep）を最優先 |
| シェルから内容検索 | `rg -n PAT dir` / `rg -l PAT dir` / `rg -F 'literal'` |
| パイプの絞り込み | `cmd \| rg PAT` / `rg -v` / `rg -c` |
| git 管理下の検索 | `git grep`（別実装なので許可されている） |
| rg が無い環境 | `ag` |

`pgrep` と `git log --grep=` は grep ではないので通常どおり使ってよい。

# ローマ字直書き入力への対応

ユーザーは iPhone など IME が使いにくい環境から、**かな漢字変換せずローマ字のまま**メッセージを送ることがある（例：`konoyouninihongowohennkannsezunyuuryokusuru`）。以下を守ること。

## 基本方針

- ローマ字直書きと判定したら、頭の中で日本語に復元してから応答する。応答自体は通常通り日本語（漢字仮名混じり）で返す。
- **復元結果をユーザーに復唱する必要は無い**（毎回「〜という意味ですね」と返すと冗長）。ただし作業の起点になる重要な指示の場合は、最初の一回だけ確認してよい。

## 曖昧性が出たときは必ず確認する

ローマ字には同音異義語・語境界・送り仮名の曖昧性がある。**勝手に解釈して作業を進めず、ユーザーに聞き返す**こと。特に以下のパターン：

- **同音異義語**：`kami`（紙/神/髪/上）、`hashi`（橋/箸/端）、`kaeru`（帰る/変える/蛙）など、文脈で一意に決まらない場合
- **語境界の曖昧性**：`konoyouni` を「この様に / 子の用に」、`ashitahareru` を「明日晴れる / 足下走れる」など、複数の区切りが成立する場合
- **固有名詞・ファイル名・コマンド名・人名**：`siori` がファイル名なのか「栞」なのか、`tanaka` が `tanaka.py` なのか「田中さん」なのか等、識別子としての可能性があるもの。**勝手にファイル名を推測して触らない**
- **数字の単位・桁**：`niman` が「2万」か「2 man（マン）」か等
- **肯定/否定の判定が割れるとき**：`yamete` が「やめて（停止指示）」か「やってみて」のタイポか不明な場合は、**破壊的操作の前に必ず確認**

## 確認の仕方

短く、解釈候補を列挙して `AskUserQuestion` で聞く。例：

> 「`kamiwosutete` は次のどちらですか？
> 　1. 紙を捨てて（ファイル削除）
> 　2. 髪を切って（別の話題）」

## タイポ補正の範囲

- 明らかな typo（`nn` の重複、`tu`/`tsu` 揺れ、ローマ字綴り違い）は黙って補正してよい。
- ただし**補正が意味を変える可能性がある場合**（例：`kesite` → 「消して」か「決して」か）は確認する。

## やってはいけないこと

- ローマ字を「英語」として扱って解釈する（`kami` を camera 関連と誤読する等）。日本語ローマ字を最優先で疑う。
- 曖昧なまま破壊的なシェルコマンド・ファイル編集・git 操作を実行する。

# Markdown の表の幅

Markdown ファイルに表を書くときは、ユーザーの Neovim で開いても折り返して崩れない幅に収める。

## ルール

- prettier で列をそろえたあとの 1 行の表示幅を **150 以下**にする。East Asian Width が W / F の文字（全角）を 2、それ以外を 1 と数える。
- 表のセルに `**`（太字）を入れない。
- URL は表に入れない。出典は表の下の箇条書きにする。

## 幅の計算

表示幅 = 各列の最大幅（最小 3）の合計 ＋ 3 × 列数 ＋ 1

- conceal で隠れる `**` やリンクの URL も幅に数える。折り返しは隠す前の幅で決まる。
- 目安：3 列なら 1 セル全角で約 23 字、5 列なら約 13 字まで。

## 収まらないときの直し方（上から順に試す）

1. 言い回しを短くする
2. 表には要点だけを残し、説明は表の直下の箇条書きに移す
3. 表を分ける、または行と列を入れ替える
4. セルが文章になる表はやめて、「太字のラベル＋箇条書き」にする

# コメント・コミットメッセージ・テスト名に書くこと

## コードコメント

コードを読んでも分からず、知らずに書き換えると壊れる、または同じ失敗を繰り返す情報だけを書く。具体的には次の 3 つ。

- 素直な書き方を採らなかった理由（例：`sort -u` ではなく `awk '!seen[$0]++'` を使うのは、元の行順を保つため）
- 試して駄目だった方法と、駄目だった理由
- 外部の制約（ツールのバグ、API の制限、仕様上の決まり）に合わせている箇所と、その制約

次のものは書かない。

- コードがしていることの言い換え（例：`# 重複を除く`）。名前や関数の切り出しで表せないかを先に考える。
- 変更の経緯（「〜を修正」「〜のために追加」「〜に変更」「以前は〜だった」）。コミットメッセージに書く。
- 作業中の依頼・会話・Issue への言及（「ユーザーの依頼で」「#12 対応」）。コミットメッセージか PR に書く。

## コミットメッセージ

- 1 行目には何を変えたかを書く。
- 本文には変えた理由を書く。きっかけになった症状や要望、その方針を選んだ理由、検討して捨てた案。
- 差分を見れば分かる変更内容を並べるだけで本文を終えない。
- typo 修正など、理由が自明な変更は本文を省いてよい。

## テスト名

- 検証する振る舞いを、条件と期待結果で書く（例：`空ファイルを渡すと何も出力しない`）。

## コメントとコミットメッセージの分け方

- コードが今この形である理由のうち、読んでも分からないものはコメントに書く。
- コードをこう変えた理由はコミットメッセージに書く。

## 理由

- コメントはコードとともに残り続ける。変更の経緯は、次にコードが変わった時点で古くなり、読み手を誤らせる。
- 採らなかった方法はコードに現れない。書き残さないと、次に読む人（次のセッションの Claude を含む）が素直な書き方に戻して同じ失敗をする。
- 変更理由はその差分に紐づく情報なので、コミットに置けば `git blame` で該当行から辿れる。
