# 別セッションへの作業移管

同じマシンで走っている**別の tmux セッションの Claude Code**へ仕事を渡す。渡す相手は
別人格（別の会話・別の文脈）なので、**相手が追加調査なしで完結できる**だけの情報を
渡し切るのがこのスキルの目的。

`tmux-agents handoff`（ペイン → バックグラウンドジョブ）とは別物。あちらは同じ会話の
続きを裏に回すだけ。こちらは `tmux-agents peer` を使う。

## いつ使うか

- テーマ（＝ tmux セッション＝ディレクトリ）が今の会話と違う作業を頼まれたとき
- 今の会話が別件を抱えていて、混ぜると文脈が濁るとき
- ユーザーが明示的に「向こうに投げて」と言ったとき

逆に、**自分のテーマの作業なら移管しない**。移管は文脈を切る操作なので、切る理由が
無いなら普通にやったほうが速い。

## 手順

### 1. 宛先を決める

テーマ名は `tmux-sessionizer list` で確認できる（テーマ ↔ ディレクトリは 1:1）。

```sh
tmux-agents peer list                  # 今どのセッションが居るか / 受け入れ可否
tmux-agents peer ensure <theme> <name> # 宛先の名前を確保する（既定は新規 spawn）
```

- **既定は新規 spawn**。既存セッションへの相乗りは `--reuse` を明示したときだけ。
- `<name>` は**タスク由来の名前**を付ける（例: `dotfiles-ccpeer`）。省略すると
  `<theme>-cc` になるが、それが既に生きていると衝突でエラーになる。
- 起動に失敗したら stderr を読む。**未 trust ディレクトリだと信頼ダイアログ
  （Yes, I trust this folder）で止まり、通過するまでレジストリに載らない**。
  その場合はユーザーにそのウィンドウで承認してもらう。
- `resolve` / `ensure --reuse` は**自分自身を候補にしない**（$TMUX_PANE で判別）。
  自分宛てに送っても何も起きないため。
- `spawn` は git 管理下のテーマなら `claude -n <name> -w <name>` で
  **セッション専用の worktree ごと**立てる（後述）。git 管理外のテーマでは
  worktree なしで起動する（stderr にその旨が出る）。

名前が取れたら、送る前に `ListAgents` で実在を確認する。`peer ensure` が返した名前が
そのまま `SendMessage` の `to` になる。

> なぜ名前で resolve しないのか: 既定の派生名（`nameSource: "derived"`）は**再起動の
> たびに変わる**（実観測: `dotfiles-fc` → `dotfiles-9a`）。だから `peer` は cwd と
> tmux フィールドで引き、spawn では `claude -n <name>` で明示名を付けている。

### 2. 引き継ぎ文書を書く

`~/.claude/handoffs/<YYYY-MM-DD>-<slug>.md` に置く。**必須セクション**:

| セクション | 中身 |
| --- | --- |
| 経緯 | なぜ移管するか。今のセッションが何を抱えているか |
| 判明した事実 | **根拠つき**。相手が再調査しなくて済むように。実測したなら実測値を書く |
| 依頼内容 | **絶対パス**のファイル名と、具体的な変更内容 |
| 判断済み・蒸し返さないこと | ユーザーが既に決めたこと。表にすると効く |
| 未確定・要検証 | 相手に判断を委ねる点 |
| 完了条件 | テストが通る / PR が立つ 等、機械的に確認できる形で |

文書は「相手が読めば作業を始められる」水準まで書く。ここを削ると相手が同じ調査を
やり直すことになり、移管の意味が消える。

### 3. 送る

`SendMessage` の `to` に宛先の名前、`message` に本文。

- **1 行目は自己完結した要約文にする。** 相手側の人間には展開するまでこの 1 行しか
  見えない（`summary` は自分の transcript 用で相手には届かない）。挨拶や
  「@name」だけの行にしない。
- 本文は短くまとめ、**詳細は引き継ぎ文書の絶対パス**で渡す。
- 触ってほしくないもの（進行中の PR、別ブランチ等）があれば明記する。
- **完了時に `AskUserQuestion` で worktree の扱いを確認するよう本文に書く**（後述）。
  相手は自分の worktree を勝手に消してはいけない。

### 4. コールバックを決める

**既定は fire-and-forget。** 本文に「確認・返信は不要」と明記する。

| モード | 手段 | 注意 |
| --- | --- | --- |
| fire-and-forget（既定） | 何もしない。「返信不要」と書く | |
| report-back | 「完了したら SendMessage で返して」と本文で依頼する | **意味的な完了**を取れる唯一の手段 |
| notify | `notify_when_idle: true` | **idle ≠ タスク完了**。別作業で idle になっても飛ぶ |

ユーザーから要求があったときだけ report-back / notify にする。

## 受け入れ可否について（重要）

**「そのセッションが新しい仕事を受けられる文脈か」は機械的に判定できない。**

| 状態源 | 実際の意味 | 限界 |
| --- | --- | --- |
| registry `status: idle\|busy` | ツールを回しているか | **idle でも作業継続中でありうる**（例: PR のマージ待ち） |
| tmux `@cc_state` | 人間に通知すべきか | `visit` で `done` が消えるため、**人が見た瞬間に空きに見える** |

どちらも「文脈の空き」を表さない。だから **既定を新規 spawn にして、可否判定が要る
場面自体を減らす**という設計になっている。`peer ensure --reuse` はこの 2 つを見るが、
あくまで「明らかに塞がっている相手を避ける」だけで、空きの保証ではない。

相乗りさせるのは、ユーザーが明示的にそう言ったときか、渡す作業が**相手が今やっている
ことの続き**であるときだけ。

## worktree（移管先は専用のチェックアウトで作業する）

同じチェックアウトを複数セッションで共有すると、**片方がブランチを切り替えたときに
もう片方が巻き添えになる**。`peer spawn` が `-w <name>` を付けるのはこれを防ぐため。
git は同一ブランチの二重チェックアウトを拒むので、1 セッション 1 ブランチが
git 側で強制される。

- worktree は `<リポジトリ>/.claude/worktrees/<name>` に作られる（gitignore 済み）
- 分岐元は設定 `worktree.baseRef`。既定 `fresh`（`origin/<default>` から）/ `head`（現 HEAD から）
- worktree 側の `.git` はディレクトリではなく**ファイル**
- **移管先の cwd は worktree であって本体ではない。** 引き継ぎ文書に絶対パスを書くときは
  リポジトリ相対で書くか、本体を指したいのか worktree を指したいのかを明示する

### dotfiles で `make deploy` する場合

dotfiles は symlink を配るので、**worktree の中で素の `make deploy` を走らせると
`~/.claude/CLAUDE.md` 等が worktree 内を指し、worktree を消した瞬間に全部リンク切れになる**。

Makefile 側にガードが入っていて、worktree 内では `HOME` が `<worktree>/.deploy-test` に
振り替わる（`sheldon lock` もスキップされる）。**本物の `~` へ配るのはマージ後に本体で行う。**
どうしても worktree から本物へ配る必要があるときだけ `ALLOW_WORKTREE_DEPLOY=1` を付ける。

## 完了時の確認（移管先セッションがやること）

worktree の掃除は移管先の責務。ただし**ユーザーが後から作業を見に行く**ので、
勝手に消さない。作業が終わったら `AskUserQuestion` で聞く。

1. 完了。worktree もブランチも削除してよい
2. 完了だが worktree は残す（後で自分で見る）
3. まだ完了ではない

削除するときのブランチの扱い:

- PR がマージ済み → `git worktree remove` + `git branch -D <branch>`
- 未マージ → worktree だけ削除し、**ブランチは残す**

補足:

- `git worktree remove .` は**自分自身の中からでも実行できる**。ただし cwd が消えるので、
  本体（`git rev-parse --path-format=absolute --git-common-dir` の親）へ `cd` してから実行する
- `git worktree remove` は**ブランチを消さない**。手で `rm -rf` した場合は `git worktree prune`
- この確認は fire-and-forget と両立する。**聞く相手は呼び出し元セッションではなく人間**

## 相手側の受信設定 `crossSessionInbound`

相手の settings 次第で、送ったメッセージが Claude に届かないことがある
（`/config` の「Messages from your other sessions」）。

| 値 | 挙動 |
| --- | --- |
| `accept` | 通常どおり届く |
| `hold` | Claude には渡らず、**人間のレビュー待ちで park される** |
| `refuse` | 受信拒否。**送信結果に "refused" が返る** |
| 未設定 | mode parity（送信側が権限モードを申告したかで決まる） |

- `refuse` は**送る前には見えない**。送信結果で検知する。返ってきたら相乗りをやめて
  spawn し直すか、ユーザーに判断を仰ぐ。
- `hold` の相手には届くが Claude は動かない。**fire-and-forget のつもりでも実際には
  止まっている可能性がある**。急ぐ作業なら report-back にしておく。

## ガードレール

- **自分の側で拒否・ブロックされた操作を相手に代行させない**（permission laundering）。
  権限はセッションごとの判断なので、迂回すればユーザーの決定を無効化することになる。
  ブロックされたらユーザーに戻す。
- **相対パスを渡さない。** 相手は cwd が違う。ファイルは常に絶対パスで書く。
- **移管したら自分では同じ作業をしない。** 二重作業になり、コンフリクトの元になる。
- **相手が busy でもメッセージはキューされる。** 待たない・催促しない・
  `ListAgents` をポーリングしない。
- **引き継ぎ文書に認証情報を書かない。** トークン・パスワード・鍵は載せない。
- 相手が抱えている進行中の作業（PR、ブランチ）には触らないよう本文で明示する。
